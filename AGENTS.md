# Claude Code Routines — Operator Guide

This repo runs **one** scheduled job: `issue-solver`, a GitHub Actions workflow
that picks one Linear task and opens one ready-for-review pull request.

The seven cloud routines this repo used to own were retired on 2026-08-06 along
with the hosting substrate they ran on. See
[`docs/RETIREMENT.md`](docs/RETIREMENT.md) for why, where each prompt's content
went, and the trigger ids that must never be reused. Do not add a new cloud
routine here — that path is gone.

## How issue-solver gets its prompt

The prompt body lives in `dryvist/ai-llm-prompts`, pinned through the
`vendor/ai-llm-prompts` submodule. This repo owns only the consumer-side
metadata:

- `routines/registry.yaml` — which catalog file to render, the pinned catalog
  commit, and the allowed-tools list.
- `.github/workflows/issue-solver.yml` — the schedule (`0 0,12 * * *`), the
  GitHub App token, the model id, and the run step.

`scripts/render-routine.sh issue-solver` strips OKF frontmatter and expands
`<!-- include: fragment-<name>.md -->` markers from the pinned catalog. It exits
nonzero on a missing or nested fragment. The workflow renders to
`.rendered-issue-solver.md` and feeds that to the run step;
`.github/workflows/render-check.yml` proves the same render works in CI.

**Changing the prompt means changing the catalog**, then advancing the submodule
and the `catalog.commit` field in `routines/registry.yaml` together. A repin
without the registry field, or vice versa, is a lie about what actually renders.

## Attribution for issue-solver PRs

Every PR it opens must be self-identifying. Three layers, all required —
without them you cannot tell an automated PR from a human one.

**Title**, conventional prefix preserved so release-please still parses it, and
no emoji anywhere:

```text
<prefix>(<scope>): <description> [routine:issue-solver]
```

**Body** ends with a Provenance block:

```markdown
---

## Provenance

- **Generated by:** [issue-solver](<prompt URL>) - GitHub Actions, twice daily
- **Triggered:** <what fired this run>
- **Why this PR:** <why this Linear task was selected>
- **Label:** `cloud-routine`
```

**Label** `cloud-routine`, applied after creation. It is defined in
`dryvist/.github` and propagated by `label-sync.yml`, so never
`gh label create` per repo.

**Branch**: `<type>/issue-solver/<slug>-<YYYY-MM-DD>`. The date prevents
collisions between runs.

PRs open review-ready, not draft, so the `ai-workflows` review workflows pick
them up. issue-solver never merges its own work.

## Rules that still bind

These lived in the retired cloud-routine ruleset but apply to any automation
here, so they stay:

1. **Commits go through the GitHub Contents API or `createCommitOnBranch`**,
   never `git commit` — a sandbox has no signing key, so a local commit lands
   unsigned and the org ruleset rejects it.
2. **No local branches.** Create refs through the API.
3. **Redact before writing.** Any string pulled from outside — file bodies, PR
   titles, issue bodies, commit messages — passes the redaction set before it
   reaches GitHub or Slack: user home paths, `GIT_HOME` variables, `GH_PAT_*`,
   `sk-ant-*`, `gh[ps]_*`, and bare 12-digit account ids. When a redaction
   fires, describe the rule that matched; never quote the string that tripped
   it.
4. **Escape Slack control tokens.** `<!channel>`, `<@USERID>`, and `<#CHANNEL>`
   can be smuggled through a PR title. Replace `<` and `>` in anything derived
   from repo content before posting.
5. **Single-owner scope.** Automation here operates on one configured owner.
   The token is scoped to that owner's repos and nothing else, so a prompt slip
   cannot reach outside it. Do not reintroduce a multi-owner loop.

## Out of scope

Cron schedules, secrets, and run history for `issue-solver` live in the
workflow and in repo secrets. There is no web UI to check any more.
